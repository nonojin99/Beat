# 리더보드 서버 검증 배포 안내

점수는 더 이상 브라우저에서 DB로 직접 들어가지 않는다.
`submit-score` Edge Function이 채보를 서버에서 다시 계산해 상한을 검증한 뒤 기록한다.

## 배포 순서

순서를 지켜야 한다. **함수를 먼저 배포하고 SQL을 나중에 실행**한다.
반대로 하면 그 사이에 나온 점수가 저장되지 않는다.

### 1. Supabase CLI 로그인 및 프로젝트 연결

```bash
supabase login
```

```bash
supabase link --project-ref ijmmqmarbkkkssciagof
```

### 2. Edge Function 배포

```bash
supabase functions deploy submit-score --no-verify-jwt
```

`--no-verify-jwt`가 필요한 이유: 클라이언트가 쓰는 publishable 키는 페이지 소스에
그대로 노출돼 있어 JWT 검증이 실질적인 보호가 되지 못한다. 검증은 함수 본문에서 한다.

### 3. 스키마 및 권한 적용

`schema.sql` 전체를 Supabase SQL Editor에 붙여넣고 실행한다.
`key_mode` / `difficulty` 컬럼 추가와 공개 INSERT 권한 회수가 함께 처리된다.
기존 점수 데이터는 보존된다.

### 4. 확인

```bash
node tools/verify-chart-parity.mjs
```

게임을 한 판 끝내고 리더보드에 기록이 올라오는지 확인한다.
실패하면 결과 화면에 사유가 표시되고, 자세한 로그는 아래에서 볼 수 있다.

```bash
supabase functions logs submit-score
```

## 검증 항목

| # | 내용 |
|---|---|
| 1 | 입력 형식 — 닉네임 길이·제어문자, 키모드 4/6, 점수·콤보 정수 및 음수 여부 |
| 2 | 곡이 카탈로그에 있는지, 그 곡에 실제로 있는 난이도인지 |
| 3 | `max_combo ≤ 해당 채보의 노트 수` |
| 4 | `score ≤ 이론상 최대 점수` (전곡 PERFECT 기준, 콤보 상한까지 반영) |
| 5 | 제출 빈도 — 같은 닉네임 기준 최소 60초 간격, 시간당 60회 |

3·4번이 성립하는 이유는 채보가 시드 고정이기 때문이다.
`(곡 · 난이도 · 키모드)`만 알면 서버가 클라이언트와 **완전히 동일한 채보**를
재생성할 수 있어서, 그 판에서 나올 수 있는 최대 점수를 정확히 계산할 수 있다.

## ⚠️ 채보 로직을 수정할 때

채보 생성 코드가 두 곳에 있다.

- `index.html` — `TRACKS`, `DIFF_PARAMS`, `KEY_MODES`, `hashSeed`, `makeRng`, `generateChart`
- `supabase/functions/submit-score/chart.ts` — 위와 동일한 로직의 서버 사본

둘이 어긋나면 **정상 점수가 반려되거나 조작 점수가 통과한다.**
난수를 소비하는 순서가 한 번만 달라져도 이후 채보 전체가 바뀐다.

곡 추가·BPM 변경·난이도 파라미터 조정 후에는 반드시 아래를 실행할 것.

```bash
node tools/verify-chart-parity.mjs
```

모든 (곡 × 난이도 × 키모드) 조합의 노트 수와 곡 카탈로그가 일치하는지 확인하고,
어긋나면 어느 조합이 몇 개 차이나는지 알려주면서 종료 코드 1로 실패한다.

## 이 방식으로 막지 못하는 것

- 함수를 직접 호출해 **그럴듯한 점수**를 넣는 것은 여전히 가능하다.
  (예: 실제로 칠 수 있는 범위 안의 점수를 60초 간격으로 제출)
- 닉네임은 인증된 값이 아니라 남의 이름으로도 제출할 수 있다.
  빈도 제한도 닉네임 기준이라 같은 이름을 쓰는 두 사람은 서로 영향을 받는다.

완전히 막으려면 플레이 중 입력 타임라인을 함께 보내 서버에서 재시뮬레이션하고
(리플레이 검증), 닉네임 대신 Supabase Auth 계정을 쓰면 된다.
지금 구조는 "콘솔에서 점수 한 줄 넣기"와 도배를 차단하는 수준이다.
